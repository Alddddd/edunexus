# EduNexUs - Workflow Logic

## Purpose

This document defines:
- core operational workflows
- role-based system behavior
- approval logic
- QR validation logic
- programmable governance rule validation
- merchant settlement lifecycle
- Morph proof recording
- verification and audit visibility
- MVP operational rules

The workflow is designed to:
- remain realistic
- support meaningful blockchain integration
- prioritize smooth demo presentation
- maintain implementation simplicity
- present EduNexUs as cooperative reimbursement infrastructure, not a crypto app

---

# 1. Core Workflow Overview

The stable EduNexUs workflow is:

```text
Member Request
-> Admin Approval
-> QR Claim Pass
-> Merchant Validation
-> Programmable Rule Validation
-> Claim Processing
-> Settlement Generation
-> Settlement Release
-> Morph Proof Recording
-> Verification Console Audit Visibility
```

The workflow must remain stable. Future improvements should add governance configurability, reporting, or audit depth without changing this core sequence.

---

# 2. Role-Based Workflow Logic

## 2.1 Admin Workflow

Admin responsibilities:
- manage assistance programs
- approve/reject requests
- manage merchants
- monitor claims
- monitor settlement lifecycle
- release merchant settlements
- review Morph proof records
- review activity/audit timelines

Admin operational flow:

```text
Login
-> Open Dashboard
-> Review Assistance Requests
-> Approve or Reject Request
-> QR Claim Pass Generated
-> Monitor Merchant Claims
-> Review Settlement Console
-> Release Settlement
-> Review Morph Verification Console
```

## 2.2 Member Workflow

Member responsibilities:
- request assistance
- track request status
- receive QR/reference claim pass
- present QR/reference to merchants

Member operational flow:

```text
Login
-> Submit Assistance Request
-> Wait for Approval
-> Receive QR Claim Pass
-> Visit Merchant
-> Present QR/Reference
-> Claim Processed if Eligible
```

## 2.3 Merchant Workflow

Merchant responsibilities:
- validate QR/reference claims
- review governance rule results
- process eligible claims
- monitor reimbursement status

Merchant operational flow:

```text
Login
-> Open Merchant Portal
-> Enter/Scan Claim Reference
-> System Runs Governance Rules
-> Review Pass/Fail Validation Result
-> Process Eligible Claim
-> Settlement Generated
```

## 2.4 Auditor / Coop Manager Workflow

Auditor responsibilities:
- monitor Morph proof records
- inspect proof bundles
- review validation summaries
- review settlement status
- verify operational transparency

Auditor operational flow:

```text
Login
-> Open Verification Dashboard
-> Review Morph Proof Records
-> Inspect Proof Bundle
-> Review Governance Validation Summary
-> Review Settlement Lifecycle
```

# 6. Programmable Governance Rule Engine

The merchant validation system now uses structured rule results. These are shown to the merchant as a readable governance review.

Current rule checks:
- claim reference verified
- approval status confirmed
- claim validity active
- merchant eligibility verified
- redemption availability confirmed
- approved amount validated

Each rule returns:
- key
- label
- passed true/false
- user-friendly message

## 6.1 Passed Validation

If all rules pass:
- merchant sees "Eligible for Claim Processing"
- claim processing is allowed
- claim is marked used
- settlement is generated
- Morph proof recording is triggered
- proof bundle and proof hash are stored in the proof payload

## 6.2 Failed Validation

If any rule fails:
- claim processing is blocked
- settlement generation is prevented
- Morph proof recording is not triggered
- merchant sees the failed rule and reason

Common failed states:
- claim validity expired
- claim already redeemed
- merchant category mismatch
- request not approved
- approved amount invalid

---

# 7. Claim Processing Workflow

After successful validation:
- assistance request is marked claimed
- `claimed_at`, `claimed_by`, and `claim_status` are updated
- member notification is sent
- settlement record is created if not already present
- claim proof recording is triggered through the Morph service
- blockchain transaction payload stores proof bundle metadata

Claim status becomes:

```text
Claimed
```

---

# 8. Settlement Lifecycle Workflow

## 8.1 Settlement Generation

After a successful claim, system creates:

```text
Pending Settlement
```

In UI language this appears as:

```text
Ready for Release
```

## 8.2 Settlement Monitoring

Admin can:
- monitor pending reimbursements
- view merchant/member/program metadata
- review settlement amount
- inspect related proof status
- see lifecycle timeline

## 8.3 Settlement Release

When cooperative reimbursement is ready, admin marks the settlement released.

Stored database status:

```text
Settled
```

UI language:

```text
Released
```

Important:
- this is not a real money transfer
- this is not stablecoin settlement
- this does not add wallets or token mechanics
- it records the operational reimbursement lifecycle

---

# 9. Morph Proof Workflow

When claim processing succeeds:
- Laravel prepares proof bundle
- Laravel generates deterministic SHA-256 proof hash
- Morph proof recording runs through the existing blockchain service
- blockchain transaction row is created
- payload stores proof hash, validation summary, and proof bundle metadata
- verification console displays proof integrity and workflow context

Proof bundle includes:
- reference code
- event type
- assistance request id
- program id
- merchant id
- member id
- approved amount
- merchant category
- validation rule summary
- status
- timestamp

The Morph Verification Console presents:
- verification status
- proof integrity labels
- rule validation summary
- lifecycle timeline

- show why blockchain matters

- avoid crypto-heavy mechanics
- reinforce tamper-resistant workflow verification

# 13. MVP Limitations

The MVP intentionally avoids:
- advanced banking logic
- partial payment computation
- multi-wallet architecture
- token systems
- stablecoin transfer
- DeFi mechanics
- real crypto settlement

Reason:
- maintain feasibility
- prioritize polished execution
- reduce technical risk
- keep blockchain as proof infrastructure
