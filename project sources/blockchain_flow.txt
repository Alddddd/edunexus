# EduNexUs - Blockchain and Proof Flow

## Purpose

This document defines:
- how Morph blockchain is used
- what data stays in MySQL
- what proof data is prepared by Laravel
- how proof bundles and proof hashes work
- how blockchain transaction payloads support audit visibility
- how the Morph Verification Console explains proof integrity

The goal is to make blockchain integration:
- meaningful
- simple
- demo-ready
- technically believable
- aligned with institutional cooperative reimbursement infrastructure

---

# 1. Blockchain Role

Morph blockchain acts as EduNexUs' tamper-resistant verification layer.

It is used for:
- claim proof recording
- workflow proof receipts
- transaction hash visibility
- audit trail support
- verification console evidence

Morph is NOT used as:
- the main database
- a wallet system for normal users
- a token economy
- a DeFi platform
- a real-time settlement rail

---

# 2. Main Architecture

```text
Laravel Web App
-> MySQL Operational Database
-> Proof Bundle Preparation
-> Deterministic SHA-256 Proof Hash
-> Morph Blockchain Service / Connector
-> Morph Transaction Receipt
-> Blockchain Transaction Payload Stored in Laravel
-> Verification Console Audit View
```

---

MySQL stores operational records:

```text
users
members
merchants
assistance programs
assistance requests
QR payloads
claim status
settlements
notifications
dashboards
proof bundle payloads
proof hashes
validation summaries
blockchain transaction logs
```

Reason:
- faster queries
- dashboard reporting
- privacy protection
- simple MVP implementation
- readable institutional audit views

---

# 4. What Goes to Morph

Morph receives proof activity through the existing blockchain service. The product treats Morph as the receipt/proof layer.

Proof records currently focus on:
- reference code / workflow reference
- claim amount
- merchant reference
- transaction hash
- timestamp / recorded state
- confirmation status

Important:
- do not store sensitive personal data on-chain
- keep personal/member details in Laravel/MySQL
- use proof hashes and references for audit linkage

Do NOT store:
- full names
- emails
- addresses
- passwords
- private documents
- medical data
- personal financial history

---

# 5. Proof Bundle Infrastructure

Laravel prepares a proof bundle when a claim is successfully processed.

Current claim proof bundle includes:
- reference_code
- event_type
- assistance_request_id
- program_id
- merchant_id
- member_id
- approved_amount
- merchant_category
- validation_rules
- status
- timestamp

The proof bundle is hashed with deterministic SHA-256. The resulting proof hash is stored in the blockchain transaction payload.

This supports:
- proof integrity presentation
- audit-ready verification console views
- readable validation summaries
- lifecycle traceability

---

# 6. Governance Validation Before Proof

Morph proof recording only happens after successful programmable rule validation.

Current governance checks:
- claim reference verified
- approval status confirmed
- claim validity active
- merchant eligibility verified
- redemption availability confirmed
- approved amount validated

If any rule fails:
- claim is not processed
- settlement is not generated
- proof bundle is not recorded for that failed claim
- merchant sees a blocked processing result

This keeps proof records meaningful: they represent validated workflow events.

---

# 7. Claim Blockchain Flow

Triggered when:

```text
Merchant successfully validates and processes a claim.
```

Flow:

```text
Merchant validates QR/reference
-> Laravel evaluates governance rules
-> All rules pass
-> Claim is marked Claimed
-> Settlement is generated
-> Proof bundle is prepared
-> SHA-256 proof hash is generated
-> Morph proof recording runs
-> Transaction hash/status returned
-> Blockchain transaction payload stored in Laravel
-> Verification Console shows proof integrity and lifecycle context
```

Stored Laravel proof payload can include:
- event type
- reference code
- claim amount
- merchant id
- merchant category
- program category
- proof hash
- proof bundle
- validation rules
- validation summary
- blockchain error if any

---

# 8. Settlement Proof / Lifecycle Context

Settlement lifecycle is currently stored in Laravel as operational reimbursement status.

Stored statuses:
- Pending
- Settled

UI lifecycle language:
- Ready for Release
- Released

Verification surfaces connect settlement status to proof records through the assistance request reference. This gives auditors context without adding real wallet or token transfer behavior.

Future settlement proof recording may be expanded, but the current MVP does not implement real crypto settlement.

# 10. Advanced Morph Verification Console

The Morph Verification Console now presents proof records as governance/audit infrastructure.

Each proof entry can show:
- verification status
- proof integrity label
- rule validation result
- settlement status
- timestamp/recorded state
- transaction hash
- proof hash
- lifecycle timeline
- proof bundle review

Lifecycle timeline:

```text
Request Submitted
-> Approved
-> Merchant Validated
-> Settlement Generated
-> Settlement Released / Release Pending
-> Morph Proof Recorded
```

Proof bundle viewer shows:
- proof hash
- event type
- reference code
- member
- merchant
- approved amount
- settlement status
- validation summary
- validation rules
- timestamp

Important wording principle:
- say "proof recorded" or "hash recorded"
- do not claim deep on-chain verification unless implemented
- do not fake tamper-detection systems

---

# 11. User Experience Principle

Blockchain must be visible only as proof, not as complexity.

Normal users should see:

```text
Proof Recorded
Verified Proof Hash
Morph Proof Confirmed
Settlement Audit-Ready
```

They should NOT need to understand:

```text
gas fees
wallet signing
smart contract internals
private keys
token transfers
```

---

# 12. Blockchain Failure Handling

If blockchain transaction fails:
- keep Laravel workflow record
- mark blockchain status as Failed
- show clear admin/audit warning
- keep proof payload available for operational review

Example:

```text
Claim processed locally, but Morph proof recording failed.
```

This prevents demo/system collapse while keeping audit status honest.

---

# 13. MVP Blockchain Success Conditions

Blockchain integration is successful if:
- claim proof recording works
- transaction hashes are returned when available
- blockchain transaction rows are saved in Laravel
- proof bundle payloads are visible
- proof hash is visible
- validation summaries are readable
- settlement context is connected
- verification console explains why Morph matters

# 14. Final Blockchain Strategy

Morph blockchain should make EduNexUs feel:
- transparent
- tamper-resistant
- payment-infrastructure aligned
- audit-ready
- technically meaningful

The blockchain layer should remain:
- simple
- focused
- invisible to normal users
- visible to judges through receipts, hashes, proof bundles, and audit timelines
